# 00 — Overview

> **TaskFlow Pro** — 팀 업무 관리 풀스택 웹 앱

---

## 문서 구성 (6개 파일 매핑)

| 파일 | 역할 | 이 파일에서 알 수 있는 것 |
|------|------|--------------------------|
| `00-overview.md` | 전체 지도 | 문서 구조, 읽는 순서, 관심사 분리 원칙 |
| `01-product.md` | 제품 정의 | 타깃 사용자, 핵심 기능, 비즈니스 목표 |
| `02-specs.md` | 기술 명세 | 기술 스택, API 설계, 데이터 모델, 환경 변수 |
| `03-design.md` | UI/UX 설계 | 화면 구성, 컴포넌트 계층, 스타일 가이드 |
| `04-tasks.md` | 개발 계획 | 마일스톤, 스프린트 태스크, 우선순위, 진행 상태 |
| `05-conventions.md` | 팀 규칙 | 코딩 컨벤션, 브랜치 전략, 커밋 규칙, PR 프로세스 |

---

## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)          (왜)           (무엇)        (어떻게)       (언제)          (규칙)
```

처음 합류하는 팀원은 `00 → 01 → 02` 순으로 읽으면 프로젝트의 목적과 기술 결정을 파악할 수 있다.  
작업을 시작하기 전에는 `04-tasks`로 현재 스프린트를 확인하고, `05-conventions`으로 규칙을 숙지한다.

---

## 왜 이렇게 나누는가 — 관심사 분리(Separation of Concerns) 원칙

하나의 문서에 모든 내용을 담으면 수정 이유가 뒤섞인다.  
제품 목표가 바뀔 때 기술 명세까지 다시 읽어야 하고, 컨벤션을 고칠 때 UI 설계가 방해가 된다.

각 파일은 **단 하나의 변경 이유**만 갖는다.

| 파일 | 변경되는 때 |
|------|------------|
| `01-product.md` | 기능 범위나 타깃 사용자가 바뀔 때 |
| `02-specs.md` | 스택 교체, API 구조 변경, 모델 수정 시 |
| `03-design.md` | 화면 흐름이나 컴포넌트 설계가 바뀔 때 |
| `04-tasks.md` | 스프린트마다, 태스크 상태가 바뀔 때마다 |
| `05-conventions.md` | 팀 합의로 규칙이 변경될 때 |

변경 영향이 한 파일 안에 격리되면 리뷰어는 diff를 좁혀서 볼 수 있고,  
협업 시 충돌(conflict) 가능성도 줄어든다.
